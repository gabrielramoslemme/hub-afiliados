# 1.2 — Base da API

## Descrição

Criar o projeto da API com a estrutura que o Hub de Afiliados vai usar até o fim: três canais de entrada separados — um para o aplicativo do afiliado, um para o painel da Porto e um para receber chamadas de sistemas externos, como o retorno de vendas da Porto nas próximas ondas.

Manter os canais separados desde o começo evita o erro mais caro possível neste produto: uma informação destinada ao painel vazar para o aplicativo, ou o contrário. A separação também deixa claro, ao ler o código, para quem cada rota existe.

Entram ainda os itens que toda rota vai usar: validação de dados de entrada, formato único de resposta de erro, verificação de saúde da aplicação e a documentação da API gerada automaticamente.

## Critérios de aceite

- [ ] A API sobe localmente com um comando e responde a uma verificação de saúde.
- [ ] Existem três canais de entrada distintos: aplicativo, painel e sistemas externos.
- [ ] Toda resposta de erro segue um formato único, com código identificável e mensagem em português.
- [ ] Dados de entrada inválidos são recusados antes de chegar à regra de negócio.
- [ ] A documentação da API é gerada automaticamente e acessível no ambiente local.
- [ ] A aplicação não sobe se faltar alguma configuração obrigatória de ambiente.

## Objetivo

Ter a API rodando com a separação de canais e os cuidados básicos de entrada e erro já resolvidos, para que cada funcionalidade seguinte só precise tratar da sua própria regra.

## Job Story

Quando eu vou construir uma rota nova, eu quero encontrar a estrutura de canais, a validação de entrada e o tratamento de erro já prontos, para escrever apenas a regra de negócio daquela funcionalidade.
