# 1.4 — Contrato de API publicado para o aplicativo

## Descrição

O aplicativo do afiliado é construído em outro repositório, por outra frente de trabalho. A ligação entre ele e a API precisa ser um documento formal, versionado e sempre atualizado — não uma conversa.

Este card entrega duas coisas. A primeira: a API passa a gerar e publicar automaticamente a especificação de todas as suas rotas a cada alteração aprovada, com as informações que entram, as que saem e os erros possíveis. Quem constrói o aplicativo consome esse arquivo e gera o cliente de comunicação a partir dele.

A segunda: os tipos de dados que o painel usa passam a ser compartilhados com a API dentro do repositório, de modo que uma mudança de formato quebre a verificação automática imediatamente.

É esse card que permite entregar as rotas do aplicativo antes mesmo de o aplicativo existir — a entrega verificável é o contrato.

## Critérios de aceite

- [ ] A especificação da API é gerada automaticamente a partir do código, sem manutenção manual.
- [ ] A especificação é publicada e versionada a cada alteração aprovada no projeto.
- [ ] Toda rota do canal do aplicativo aparece na especificação com dados de entrada, de saída e erros possíveis documentados.
- [ ] Os tipos de dados usados pelo painel são compartilhados com a API dentro do repositório.
- [ ] Uma alteração de formato feita na API que quebre o painel é apontada pela verificação automática antes da aprovação.
- [ ] A verificação automática roda em toda alteração proposta e reprova código que não passe em estilo, tipos, testes ou build.

## Objetivo

Ter o contrato da API publicado e versionado, para que a frente do aplicativo trabalhe em paralelo, sem depender de alinhamento verbal nem de o aplicativo estar pronto para validarmos nossas rotas.

## Job Story

Quando eu construo o aplicativo do afiliado, eu quero uma especificação sempre atualizada das rotas da API, para gerar meu cliente de comunicação e avançar sem depender de conversa com o time da API.
